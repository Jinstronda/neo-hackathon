- Diagnosed why GitHub showed zero CI check-runs for PR #1 despite retest-gate running successfully on every push: confirmed via `gh api .../check-runs` for the PR's exact head SHA (0 results) that the original push from the blue agent's automated session never delivered a webhook, while an ordinary `git push` from this session did. - That real run then failed on `pytest -q tests`: the static suite in `tests/` assumes `demo-target/app.py` is still the pristine, unpatched baseline (`tests/_patch.py` applies FIXES.md's own transform and needs the original vulnerable anchors to exist), which holds on `master` but never holds on a fix PR's own branch, since the branch's whole point is that the patch is already applied there. Moved the static suite to run only on `push` (where the assumption is true), kept it off the `pull_request` job, since the twin-replay step is the real per-PR proof and already decides pass/fail from server-side state. Evidence: the original failing run (44746101881, "fix anchor missing... FIXES.md drifted from app.py"); the fixed passing run (44746592991). [certain, two-way]
- While fixing that, found a second, more serious bug via an automated security review I verified myself: the replay step was `python -m infra.replay ... | tee retest-events.jsonl` with no `pipefail`, and the job's actual shell was logged as `bash -e {0}` (errexit only, confirmed from the raw run log, not assumed), so a post-patch exploit still succeeding (`gate_pass: false`) would have reported CI success anyway, since `tee`'s exit code (always 0) is what `-e` without `pipefail` checks. Verified both directions empirically, not just by reading the fix: opened a disposable PR (#16) from a branch with the SQL injection deliberately left unpatched, the step correctly failed, then closed PR #16 and deleted its branch. Evidence: run 44746935152 (failed, as it should); PR #16 close comment; the final real run on PR #1, 44747165182 (passes, because its patch is actually correct). [certain, one-way in effect: this is the core safety guarantee of the whole submission, so I verified it by inducing the failure case, not just reading the YAML]
- Applied both CI fixes to `master` and cherry-picked them onto `neo/fix-A1` (PR #1's branch) separately, since GitHub evaluates `pull_request`-triggered workflows from the PR's own head branch, not from master. Evidence: commits `172ecfb`, `0a6ee24` on master; `8554427`, `656c7b5` on `neo/fix-A1`. [certain, two-way]

Chose set-equality over `len(approvers)==2` so two approvals from one reviewer, or an approve-then-request_changes, cannot merge. Evidence: `console/ops/cloud_runner.py` merge_ready(); `qa/contract/test_cloud_runner.py` test_merge_gate. [certain, two-way]
